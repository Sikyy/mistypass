# MistyPass 生产部署方案评估（Fly.io vs Kubernetes）

> 评估日期：2026-04-18  
> 范围：`api` + PostgreSQL + Redis + EMQX 的生产部署形态

当前能力状态：

- `CONTRACT_READY`：生产部署候选、约束与推荐方向已明确，可作为基础设施选型与落地实施的评审基线。

## 1. 评估目标

- 在可控运维成本下完成 MVP 到首批生产租户上线。
- 满足可观测性、可回滚、横向扩展和安全基线要求。
- 避免过早进入高复杂度平台运维。

## 2. 候选方案

### 2.1 Fly.io（轻运维）

- 适合早期团队：部署门槛低、交付速度快。
- 内置全球边缘能力，适合单体 API 快速上线。
- 对多组件编排（EMQX、PgBouncer、复杂状态服务）灵活度有限。
- 跨云/跨环境一致性与平台可迁移性弱于 K8s。

### 2.2 Kubernetes（自建或托管）

- 适合中长期：多服务治理、弹性、可观测性、策略控制更完整。
- 可统一纳管 API/Worker/EMQX/PgBouncer 等组件并做标准化发布。
- 初期学习和运维成本高于 Fly.io。
- 需要配套 CI/CD、镜像仓库、Ingress、证书、告警体系。

## 3. 对比结论

| 维度 | Fly.io | Kubernetes |
|---|---|---|
| 上线速度 | 高 | 中 |
| 运维复杂度 | 低 | 高 |
| 多组件编排能力 | 中 | 高 |
| 扩展与治理能力 | 中 | 高 |
| 可迁移性 | 中 | 高 |
| 早期团队匹配度 | 高 | 中 |
| 中长期规模匹配度 | 中 | 高 |

## 4. 推荐策略（分阶段）

1. 阶段 A（当前到首批租户）：优先 Fly.io，目标是最短路径上线验证业务闭环。  
2. 阶段 B（租户增长后）：切换到托管 Kubernetes（建议 EKS/GKE/ACK 任一），将 API、后台 Worker、EMQX、PgBouncer 统一纳管。  
3. 阶段 C（稳定运营）：完善 GitOps、弹性策略、成本监控和多环境发布策略。

## 5. 落地基线（无论选哪种平台）

- 强制 TLS 终止与证书自动续期（对应清单 `5.7.3`）。
- API 前置反向代理/网关并启用限流、WAF 基础策略。
- 数据层至少启用 PostgreSQL 自动备份与恢复演练。
- Redis 开启持久化策略并配置容量/淘汰策略告警。
- 统一接入日志、指标、链路追踪与告警（现有 OTel + Prometheus 基线延续）。

## 6. 决策建议

- 当前建议：**先 Fly.io，后 Kubernetes**。  
- 触发迁移阈值建议（满足任一即可启动迁移）：
  - 日均活跃租户超过 50 且增长持续；
  - API/Worker/EMQX 多组件联动发布频率显著提升；
  - 需要细粒度隔离、配额策略与多环境标准化运维。
